# #6：主库与 WAL 的只读一致采集

依据用户对 [#6](https://github.com/ai-daming/wxview/issues/6) 的实施授权。范围是原始数据读取；提交、发布和后台进程操作分别按已有授权执行。

## 决定

- 在公共 decrypt 层实现只读主库／WAL 快照：保留打开的文件，先校验 WAL 并建立最后已提交页的偏移映射，再逐页解密到临时缓存。内存只随 WAL 中不同页数增长，不一次载入整个主库或 WAL；不生成额外原始数据副本。
- 校验 WAL 头、校验和字节序、代际、帧校验和与提交边界；排除未提交事务和旧代际尾部。处理增长、截断后再增长的缺页，禁止把已截断主库旧页当作新页复活。检测到 rollback journal 时不猜测恢复内容。
- 采集前后比较主库／WAL 的存在性、大小、纳秒 mtime、WAL 头及文件身份。源发生变化时最多重试三次；校验、解密、SQLite 验证和稳定性检查均在发布前完成。失败不替换旧缓存。
- 解密成功返回实际采集的源签名，key 层直接保存它，不能在发布后重新 stat 并把另一个源版本记成已读。现有 mtime.json 增加 WAL 和快照版本字段；旧条目需刷新一次，不另建状态文件。
- daemon 继续共享已有账号／路径快照，仅将每个数据库的 WAL／journal 加入轻量文件监视；不增加账号探测频率。
- 新快照缓存发生变化后，旧索引先回退扫描，不能用旧的 60 秒宽限掩盖新消息；索引匹配缓存后恢复快路径。旧格式缓存原有策略保留。
- 单库提交视图不代表全账号多库同一时刻，也不承诺跨分页缓存刷新的一致快照。查询接口、原文和检查点语义不变。#7 的新元数据接口不纳入本项。

## 验证次序

1. WAL 事务、校验、代际、增长／截断及缺页的测试先失败再实现；加入取消、读取中变化、失败保留旧缓存。
2. 合成真实 SQLite 数据验证密钥复用、WAL-only 刷新、缓存状态、直接消息查询与索引失效／恢复。
3. 覆盖 daemon 触发与 CLI／WebAPI 查询刷新入口，保持 GET 只读、增量预览不推进状态。
4. 运行受影响模块测试、必要交互、race／vet 和 Windows 交叉编译；不运行全仓回归。
5. 真实微信双标记及平台实测单独记录。没有相应环境或授权时保留未完成，不用合成成功代替。
